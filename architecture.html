스키마(확정 v12): 스키마 페이지 · 태그: 신규 새로 만드는 것 · 재사용 기존 시스템 그대로 · 하드웨어
🔑 핵심 아키텍처 결정 (민철 확정 2026-07-26): V2는 별도 서비스가 아니라 SkinSeoulFacade `apps/internal-api` 안의 새 도메인(`domain/wms2`) + 기존 Cloud Spanner 인스턴스에 신규 DB로 짓는다. 이유 — ① 배포 파이프라인·인증(ApiKeyGuard/JWT)·모듈 패턴 재사용, ② V1(DDB)과 같은 프로세스에서 병행 운영 → 컷오버가 라우팅 스위치 수준, ③ DB 신설 인프라 0 — dev/staging/prod Spanner 인스턴스가 이미 라이브(운영·백업·failover·DDL 절차 기존 것 그대로), Gigwork 주문과 같은 DB라 JIT 연동이 로컬 조인. 프론트는 기존 AdminDashboard에 화면 8종 추가 — 신규 앱 없음.
⚙️ Spanner 전환에 따른 설계 조정 3건 (스키마 v12 자체는 불변 — 구현 방식만): ① 트리거 없음 → rollup_status·total_quantity 재계산은 OrderRollupService 단일 갱신 경로로 강제(라인을 바꾸는 모든 핸들러가 같은 txn에서 호출 — 경로가 하나라 stale 불가) ② partial UNIQUE 없음 → 마케팅 멱등(R8)은 generated column + NULL_FILTERED unique index(동일 효과) ③ 순차 발번 핫스팟은 초당 수천 write 얘기 — 현 볼륨(하루 수백~수천 주문)에선 무해, 7/6 확정(사람이 읽는 순차 번호) 그대로.
📮 Queue 안 만든다 (민철 논의 확정): WC push는 요청받은 pod가 건별 비동기(캡 5~10/pod) — 실패는 시간당 스위퍼가 곧 재시도 큐(전달 보장 이미 확보, pod 간 조율 불필요). 스케줄 실행(스위퍼·배치)은 기존 SkinSeoulBatch(GCP Batch) 재사용 — 잡은 internal-api의 wms2 엔드포인트를 호출만 하고 로직은 도메인 안에(확립된 batch→internal-api 패턴), 단일 실행 보장이라 리더 선출 불요. 스캔/출고는 동기 트랜잭션(Queue 금지 영역). 대량 파이프라인(수만 건 임포트·대량 라벨)이 실제로 생기면 그때 Cloud Tasks로 — 미리 깔 이유 없음.

소프트웨어 구조 — domain/wms2 클래스 다이어그램 (인터랙티브)

기존 Facade 컨벤션 그대로: Controller(얇게) → 유스케이스당 Handler 1클래스 → 도메인 서비스 → 테이블당 Repository 1클래스. 노드를 클릭하면 연결이 하이라이트되고, 시나리오 버튼을 누르면 그 시나리오가 지나가는 경로가 순번과 함께 표시된다.
시나리오 경로:
사용법 — 노드 클릭: 그 클래스가 누구를 부르고 누구에게 불리는지. 시나리오 버튼: 요청 하나가 코드 어디를 지나가는지 ①②③ 순번으로.
읽는 법 — StockLedgerService: stock_movement(원장)와 stock_balance를 쓰는 유일한 클래스. 다른 어떤 코드도 재고를 직접 못 만짐(V1은 아무 핸들러나 카운터를 증감해서 드리프트). · ReservationService: 예약의 5개 전이(reserve→flip→consume/release)가 전부 여기 — SSD-4448(예약 영구 잠김)이 구조적으로 불가능해지는 지점. · OrderRollupService: Spanner엔 트리거가 없어서 앱이 rollup을 재계산하는데, 경로를 이 한 클래스로 강제해 stale을 막음. · CatalogGateway: 카탈로그 미러 금지 결정의 코드 형태 — WP를 그때그때 조회.

핵심 트랜잭션 — 출고 스캔의 실제 흐름 (단계별 재생)

이 그림이 V1과 갈리는 지점: V1은 출고 때 가용성 산식(available = total − reserved + 자기예약)을 다시 계산했고, 그 산식과 카운터 드리프트가 SSD-4448의 뿌리. V2는 예약 행의 상태전이 하나로 끝난다 — 산식 자체가 없다.
