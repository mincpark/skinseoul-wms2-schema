OMS/WMS 2.0 — 시스템 아키텍처 (v2 · Spanner 확정 반영 · 스키마 v12 기반 · SSD-4967)

스키마(확정 v12): 스키마 페이지 · 태그: 신규 새로 만드는 것 · 재사용 기존 시스템 그대로 · 하드웨어
🔑 핵심 아키텍처 결정 (민철 확정 2026-07-26): V2는 별도 서비스가 아니라 SkinSeoulFacade `apps/internal-api` 안의 새 도메인(`domain/wms2`) + 기존 Cloud Spanner 인스턴스에 신규 DB로 짓는다. 이유 — ① 배포 파이프라인·인증(ApiKeyGuard/JWT)·모듈 패턴 재사용, ② V1(DDB)과 같은 프로세스에서 병행 운영 → 컷오버가 라우팅 스위치 수준, ③ DB 신설 인프라 0 — dev/staging/prod Spanner 인스턴스가 이미 라이브(운영·백업·failover·DDL 절차 기존 것 그대로), Gigwork 주문과 같은 DB라 JIT 연동이 로컬 조인. 프론트는 기존 AdminDashboard에 화면 8종 추가 — 신규 앱 없음.
⚙️ Spanner 전환에 따른 설계 조정 3건 (스키마 v12 자체는 불변 — 구현 방식만): ① 트리거 없음 → rollup_status·total_quantity 재계산은 OrderRollupService 단일 갱신 경로로 강제(라인을 바꾸는 모든 핸들러가 같은 txn에서 호출 — 경로가 하나라 stale 불가) ② partial UNIQUE 없음 → 마케팅 멱등(R8)은 generated column + NULL_FILTERED unique index(동일 효과) ③ 순차 발번 핫스팟은 초당 수천 write 얘기 — 현 볼륨(하루 수백~수천 주문)에선 무해, 7/6 확정(사람이 읽는 순차 번호) 그대로.
📮 Queue 안 만든다 (민철 논의 확정): WC push는 요청받은 pod가 건별 비동기(캡 5~10/pod) — 실패는 시간당 스위퍼가 곧 재시도 큐(전달 보장 이미 확보, pod 간 조율 불필요). 크론 단일 실행은 K8s CronJob(리더 선출 불요). 스캔/출고는 동기 트랜잭션(Queue 금지 영역). 대량 파이프라인(수만 건 임포트·대량 라벨)이 실제로 생기면 그때 Cloud Tasks로 — 미리 깔 이유 없음.

이 그림이 V1과 갈리는 지점: V1은 출고 때 가용성 산식(available = total − reserved + 자기예약)을 다시 계산했고, 그 산식과 카운터 드리프트가 SSD-4448의 뿌리. V2는 예약 행의 상태전이 하나로 끝난다 — 산식 자체가 없다.
